# Frontend-Backend Responsibility Boundary (Clew)

> This document defines the responsibilities and security boundaries borne by `prototype/frontend` (React SPA) and `prototype/backend` (FastAPI + SQLite), serving as the basis for subsequent evolution, review, and division of new features. The conclusions describe only behavior already implemented in the current prototype; see §9 for gaps.

---

## 1. Introduction and Positioning

Clew is a field-level lineage tool built as "single process + single relational database" (Design §8). The frontend is a pure consumer: it reads and writes the backend only through REST/JSON (JWT authentication), never connects to the database directly, and never parses source files. This document answers four questions:

1. Which validations and invariants are enforced by the backend while the frontend only performs UX optimization;
2. What the frontend and backend each do in every feature domain (authentication, import, editing, versions, AI, etc.), and how errors are divided;
3. Where the read/write boundary of AI capabilities lies (tools are read-only; suggestions require human confirmation);
4. Which current known gaps are unclosed boundaries (e.g., the missing user role change endpoint).

## 3. Overall Boundary Principles

The following principles all trace back to the sources above and are the starting point for the responsibility matrix and the prohibited actions (§8) that follow.

| # | Principle | Basis |
|---|---|---|
| P1 | **The backend SQLite is the only source of truth**: current state is read and written directly against the base tables, and all historical capabilities (diff/rollback) are derived from `change_log`; the frontend neither holds nor adjudicates any persistent state | Data Model §7; Design §4.2 |
| P2 | **All nine business invariants are guaranteed by the backend** (no storage without a locator, locator normalization, edge uniqueness, AI cannot take effect directly, annotations are append-only, every write leaves a trace, versions are revertible, permission tiers, keys are never stored in the database); the frontend may "help users make fewer mistakes" but does not participate in enforcing any invariant | Business Model §6; see Data Model §8 for where they are enforced |
| P3 | **Permissions always follow the backend `require_role` guard**: each route declares a minimum role (viewer < editor < admin), and the role is taken from the database's current value; hiding write entry points by role in the frontend is only UX, not a security boundary | Design §4.4; `prototype/backend/src/lineagelite/security.py` (`require_role` comment: "the role is taken from the database's current value"); `prototype/frontend/src/lib/roles.ts` (comment: "real permission checks always happen in the backend") |
| P4 | **Actor identity cannot be forged**: `change_log.actor`, `annotation.author`, and `created_by` on every table are always taken from the JWT `sub`; the frontend has no field that can specify them | Business Model §6-6; Design §4.4 ("author/actor are both taken from the JWT and cannot be forged") |
| P5 | **Real-file verification and locator materialization happen only in the backend**: `src_locator.resolved` is parsed from the hosted source file and written by the backend; any `resolved` sent by the frontend is discarded and recomputed | Data Model §4-4.1; module comment in `prototype/backend/src/lineagelite/routes/fields.py` |
| P6 | **Single rendering entry point**: every "fetch subgraph" capability returns `GraphPayload`; search results, click-to-expand, and AI conversation graphs share the same frontend rendering path, and the frontend maintains no second graph data structure | Design §5.2; `prototype/frontend/src/components/Workspace.tsx` (`applyGraph` serves both regular subgraphs and AI graphs) |
| P7 | **No push, pure request-response**: the backend maintains no UI state (collapse, filter, selection); after a write, the frontend actively re-fetches to refresh | Design §8 (synchronous writes, no message queue); frontend components call `refreshGraph/refreshAll` after successful writes |
| P8 | **Keys and storage paths never leave the backend**: LLM keys exist only in the deployment environment's `.env`; source file `storage_path` never appears in any API response, and downloads/previews go through controlled endpoints | Business Model §6-8/9; `prototype/backend/src/lineagelite/routes/files.py`, `routes/ai.py` |

## 4. Responsibility Matrix

Each domain has four columns: frontend responsibilities / backend responsibilities / invariant and validation ownership (backend service layer / database constraints / frontend does not participate) / error handling division (who intercepts, how it is displayed). General conventions: all requests go through the `request()` wrapper in `prototype/frontend/src/lib/api.ts` and carry `Authorization: Bearer <token>`; global 401 handling is described in §5; write entry points are shown or hidden by `isEditor/isAdmin` (`lib/roles.ts`).

### 4.1 Authentication and Token Lifecycle

| Frontend responsibilities | Backend responsibilities | Invariant and validation ownership | Error handling division |
|---|---|---|---|
| Login form (`LoginPage`); session `{access_token, username, role}` persisted to `localStorage` (`SESSION_STORAGE_KEY`); logout calls `clearSession`; when any token-bearing request receives 401, `AUTH_EXPIRED_EVENT` is dispatched and `App.tsx` clears the session and returns to the login page | `POST /auth/login` verifies the pbkdf2 password hash and issues a JWT (HS256, `exp = jwt_expire_hours`); each protected route decodes the Bearer token via `current_user`, then **re-queries the database role** via `require_role` (after a role change, an old token immediately takes effect with the new role, `security.py`) | Passwords are stored only as salted hashes (Design §4.1 `user.password_hash`); token validity, expiry, and role are all determined by the backend; the frontend does not parse JWT contents and does not keep a local expiry timer | Backend 401 ("invalid username or password", without distinguishing a nonexistent user from a wrong password; invalid/expired token; user deleted); the frontend `request()` intercepts 401 → global return to the login page (§5); login failure reasons are shown in the login form |

## 5. Authentication and Authorization Boundary (Dedicated Section)

1. **Issuance and validation belong entirely to the backend**: JWT issuance (`create_token`, HS256 + `exp`), Bearer decoding (`current_user`), and role determination (`require_role`) all live in `prototype/backend/src/lineagelite/security.py`. Key implementation detail: `require_role` **re-queries the current `user.role` value from the database on every request**; the role in the JWT is only a snapshot taken at login — therefore, once the (future) role change endpoint lands, old tokens immediately have their permissions tightened without waiting for expiry.
2. **Frontend responsibilities and risks of holding the token**: `lib/api.ts` stores the `Session` (including `access_token`) as plaintext JSON in `localStorage` (key `clew.session`) and restores the session after a page refresh; it clears it on logout/expiry. This is an explicit trade-off in the prototype (README M3 section): the risk is that a same-origin XSS script can read the token; the prototype does not introduce httpOnly Cookie / refresh token mechanisms (that risk and its mitigation are future evolution decisions, [TBD-FE]).
3. **Global 401 handling chain**: any token-bearing request receiving 401 → `request()` dispatches `AUTH_EXPIRED_EVENT` (the independent fetch path in `downloadSourceFile` is handled the same way) → `App.tsx` listens, calls `clearSession`, and switches back to `LoginPage` with the message "your session has expired; please log in again to continue". The frontend **does not predict local token expiry**; a backend 401 is the only expiry signal.
4. **Viewer UI hiding vs backend enforcement**: `isEditor/isAdmin` in `lib/roles.ts` only determines whether write entry points render (canvas `nodesConnectable`, edit/delete buttons, tag creation form, rollback button, user management entry, AI confirm button). **Hiding in the frontend is not a security boundary**: calling a write endpoint directly with a viewer token is rejected by the backend `require_role` (403 "X role or above required"); the frontend has unified copy for this fallback 403 (`readErrorDetail`: "the current account is not allowed to perform this operation"). When reviewing any new feature, the criterion is "would the permission still hold with the frontend removed?"
5. The role hierarchy is fixed as `viewer < editor < admin` (`ROLE_ORDER`), consistent with Design §4.4 and Business Model §2; no object-level ACL is implemented (all datasets in the workspace are visible; for `[TBD-BIZ]` dataset-level privatization, see the remaining open items in Design §10).

## 6. Data Contract Boundary

1. **Type correspondence**: the frontend `prototype/frontend/src/types.ts` corresponds one-to-one with the backend `models.py` (request-side pydantic: `UserCreate`, `FieldPatch`, `EdgeCreate/EdgePatch`, `AnnotationCreate`, `VersionTagCreate`, `AiChatIn/AiSuggestIn/AiEdgeKeyIn`) and each route's response dict. Naming convention: field names are transmitted as-is in snake_case (e.g., `from_dataset`, `field_count`), and the frontend does not convert to camelCase. Representative correspondences: `Session ↔ TokenOut` (`/auth/login` response), `DatasetSummary ↔ GET /datasets` (including the contract increment `field_names`), `LineageGraph/LineageEdge ↔ GraphPayload` (`edges[].id` is the database primary key, which M3 edits use for targeting, Data Model §9.1), `PreviewResponse ↔ /fields/.../preview` (including the `file/verification` increments).
2. **Time and ID serialization**: backend times are always UTC ISO 8601 strings (`isoformat(timespec="seconds")`, e.g., `now()` in `routes/files.py` and `changes.py`); the frontend only formats them for display (`formatDateTime` in `lib/format.ts`) and makes no parsing assumptions beyond timezone conversion. IDs fall into three categories with agreed transport forms: dataset uses the user-defined string `id`; edge has both an auto-increment primary key `id` (for edit/delete) and a four-part natural key (for AI confirm/reject, `AiEdgeKeyIn`); entity history/annotation targets use the `entity_key` string from Data Model §5.2 (`ds.field`, `from-->to`, where `.*` may be omitted at table level) — `edgeEntityKey` in `lib/entities.ts` assembles it on the frontend, but **validity is ultimately checked by the backend application layer** (ambiguity 400).
3. **Error response structure**: the backend error body is FastAPI's standard `{detail: <string>}`; on parameter validation failure, `detail` is a pydantic array `[{loc, msg, ...}]`. The frontend `readErrorDetail` (`lib/api.ts`) consumes it uniformly: it prefers the string `detail` verbatim; for arrays, it concatenates the `msg` values (joined with `；` in zh and `, ` in en); when missing, it falls back to an i18n message keyed by status code (fixed copy for 401/403/404/409/422). **Echoing 409 reasons is an explicit frontend responsibility**: for field locator verification failures (§4.8), duplicate edges, and duplicate tag/username conflicts, the backend `detail` is always the full English reason, and the frontend presents it verbatim without rewriting it.
4. **Contract evolution rules**: increments of the code relative to Design §4 are governed by Data Model §9 (three batches M2/M3/M4); new endpoints must be registered in sync to prevent drift between documentation and `prototype/backend/src/lineagelite/`. Complete field-level request/response tables are not repeated here; see ./05_api-reference.md; for deployment and module structure, see ./01_architecture.md.

## 7. AI Boundary (Dedicated Section)

1. **Tools are read-only**: the toolset exposed to the model by `/ai/chat` is `search_fields`, `get_field_details`, `trace_lineage`, `get_field_history` (`prototype/backend/src/lineagelite/ai/tools.py`); all are read-only queries against SQLite and never write to the database (Data Model §9.3). The conversation itself (viewer+) can never produce any data change.
2. **System prompt belongs to the backend**: the model system prompt is assembled by the backend (including optional focus context), and `AiChatMessage.role` is restricted to `user/assistant` — the frontend cannot inject instructions to override tool constraints (comment in `models.py`: "avoid the frontend overriding tool constraints"; comment in `AiAssistantDrawer.tsx`: "the system prompt is fixed by the backend").
3. **Visibility and presentation of `source='ai'`**: AI candidate edges are real edge rows (low confidence, `source='ai'`) delivered normally with the subgraph; the frontend distinguishes the source with `SourceBadge` and provides **purely local filtering** ("hide AI edges / confirmed only / minimum confidence") that makes no backend request and deletes no data. The "hide low-confidence AI edges" filter from Design §5.1 is implemented by the frontend; this is one of the few "presentation-layer invariants" explicitly assigned to the frontend — it affects display only and does not affect rollback/confirmation semantics.
4. **Division of confirm-promotion and reject-deletion** (Business Flow §5.6 / Data Model §9.3):
   - Frontend: the entry is in edge details (it does not depend on candidate cards in memory and remains operable after refresh); the confirm button is visible only to editor+; after success, a refresh makes `source` become `manual`.
   - Backend: `confirm` rewrites `source='ai'` to `manual` and writes an `updated` log — **the invariant "human confirmation by editor or above" (#4) is enforced by the backend role guard**; `reject` deletes the candidate edge and writes a `deleted` log (equivalent to a normal edge deletion, restorable by tag rollback).
   - Boundary implication: AI never directly produces official lineage; "confirm" is an ordinary human write operation that reuses the edge's trace and rollback mechanisms.
5. **Keys and configuration**: the LLM key exists only in the deployment environment's `.env` (business rule #9); `/ai/status` reports only `configured/model`; when unconfigured, `/ai/chat` returns 503, and the frontend uses this to guide configuration instead of retrying with an error.

## 8. Prohibited Actions Checklist

Derived from the §3 principles; follow the checklist (Pass/Fail) during review.

**Frontend prohibitions:**

1. Do not parse source files or materialize locators yourself (`resolved` is always computed by the backend; a frontend-supplied value is discarded) — P5.
2. Do not treat role-based hiding as a permission fallback (hiding an entry ≠ prohibiting the operation; all permissions follow the backend 403) — P3.
3. Do not forge/specify the actor (do not send `actor/author/created_by`-type fields; they are always taken from the JWT by the backend) — P4.
4. Do not assemble default values for controlled fields such as `source` and `role` on the frontend to bypass semantics (`source='manual'` on edge creation is forced by the backend; user `role` is validated by the backend pattern).
5. Do not compute diff / rollback results locally in place of backend endpoints (`change_log` merging and reversal idempotency are guaranteed only in the backend) — P1.
6. Do not inject system role messages or forge tool invocation traces in AI requests (role can only be `user/assistant`).
7. Do not cache sessions to bypass 401 (on receiving 401, the global logout chain must be followed; no silent retries).

**Backend prohibitions:**

1. Do not return `storage_path`, absolute filesystem paths, or LLM keys/configuration values in any response — P8.
2. Do not provide write routes that bypass `require_role`; new routes must declare a minimum role — P3.
3. Do not accept a frontend-specified actor identity; do not perform writes without a `change_log` entry (except for the whitelist in Data Model §9.4: annotation creation and tag creation/rollback) — P2/P4.
4. Do not maintain or query UI state (collapse, filter, selection, Toast); the backend recognizes only request parameters — P7.
5. Do not introduce push channels that change the request-response model (evolution first requires revising this boundary document and ./01_architecture.md).
6. Do not let `resolved` computation diverge from hosted source files (verification must open the real file in `data/files/`) — P5, business rule #1.
